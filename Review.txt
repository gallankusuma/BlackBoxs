# 4. Development Action List

## AST-001 — Backend RBAC belum diterapkan

**Severity:** P0 — Critical
**Status:** Open

Seluruh endpoint Asset Management hanya menggunakan `authMiddleware`. Setiap user desktop yang memiliki JWT dapat:

* Membuat dan menghapus production line
* Membuat dan menghapus P&ID
* Membuat, mengubah, dan menghapus aset
* Mengubah harga perolehan
* Mengubah umur ekonomis dan nilai residu
* Menghapus dokumen
* Menghapus maintenance
* Menghapus riwayat penambahan nilai

Tidak ada pemeriksaan permission seperti `assets.create`, `assets.edit`, atau `assets.dispose`.

### Tindakan

Tambahkan permission minimal:

```text
assets.view
assets.create
assets.edit
assets.delete
assets.dispose
assets.documents.manage
assets.maintenance.view
assets.maintenance.manage
assets.financial.view
assets.financial.manage
assets.master.manage
```

Gunakan middleware:

```ts
authMiddleware,
requirePermission('assets.create')
```

### Acceptance criteria

* User Viewer hanya dapat menggunakan endpoint GET.
* Asset Officer dapat membuat dan memperbarui data operasional.
* Maintenance Officer hanya mengelola maintenance.
* Finance hanya mengelola nilai finansial dan depresiasi.
* Disposal hanya dapat dilakukan role berwenang.
* Akses tidak sesuai menghasilkan HTTP `403`.
* Permission diverifikasi backend, bukan hanya menyembunyikan tombol frontend.

## AST-002 — Menyimpan detail aset dapat menghapus P&ID dan spec

**Severity:** P0 — Critical
**Status:** Open

Endpoint `PUT /assets/:id` melakukan full replacement terhadap:

```text
pnid_id
spec
production_line_id
```

Namun `editForm` di `AssetDetail.vue` tidak membawa `pnid_id` maupun `spec`.

Akibatnya, ketika user hanya mengganti nama atau status:

* `pnid_id` dapat berubah menjadi `NULL`
* `spec` dapat berubah menjadi `{}`

Aset kemudian hilang dari daftar P&ID dan spesifikasi lama terhapus.

### Tindakan

Pilih salah satu:

1. Ubah endpoint menjadi `PATCH` dan hanya update field yang dikirim; atau
2. Frontend wajib mengirim seluruh data existing; atau
3. Backend mengambil data existing lalu melakukan merge.

Pendekatan yang direkomendasikan:

```ts
PATCH /api/assets/:id
```

### Acceptance criteria

* Mengubah nama tidak mengubah `pnid_id`.
* Mengubah status tidak menghapus `spec`.
* Mengubah harga tidak mengubah lokasi atau P&ID.
* Automated test memastikan field yang tidak dikirim tetap utuh.

## AST-003 — Metode saldo menurun belum diimplementasikan

**Severity:** P1 — High
**Status:** Open

Frontend menyediakan:

```text
straight_line
declining_balance
```

Tetapi fungsi `calcDepreciation()` selalu menggunakan rumus garis lurus dan tidak membaca `depreciation_method`.

### Risiko

User dapat memilih saldo menurun, tetapi hasilnya tetap garis lurus. Laporan aset menjadi menyesatkan.

### Tindakan

Pilih salah satu:

* Implementasikan saldo menurun lengkap beserta rate; atau
* Hapus pilihan saldo menurun sampai implementasinya tersedia.

Tambahkan unit test untuk setiap metode.

### Acceptance criteria

* Metode yang dipilih menghasilkan rumus yang sesuai.
* Saldo menurun memiliki rate yang jelas.
* Nilai buku tidak turun melewati nilai residu.
* Perhitungan dapat diuji pada tanggal tertentu menggunakan parameter `as_of_date`.

## AST-005 — Penghapusan permanen merusak audit trail

**Severity:** P1 — High
**Status:** Open

Endpoint berikut melakukan hard delete:

```http
DELETE /api/assets/:id
```

Database menggunakan cascade untuk dokumen, maintenance, dan purchase history. UI bahkan menjelaskan bahwa seluruh histori ikut terhapus.

### Risiko

* Jejak aset perusahaan hilang permanen.
* Histori maintenance dan nilai finansial tidak dapat diaudit.
* Aset yang sudah pernah digunakan atau didepresiasi dapat dihapus.

### Tindakan

Gunakan:

```text
is_deleted
deleted_at
deleted_by
deletion_reason
```

Aturan:

* Draft yang belum pernah digunakan boleh dihapus.
* Aset aktif tidak boleh hard delete.
* Aset berhistori harus melalui disposal.
* Hard delete hanya untuk administrator database dan bukan melalui UI normal.

### Acceptance criteria

* Aset aktif tidak dapat dihapus permanen.
* Data disposed tetap tersedia dalam laporan histori.
* Dokumen dan maintenance tetap tersimpan.
* Penghapusan logical tercatat di audit log.

## AST-006 — Disposal belum menjadi proses bisnis

**Severity:** P1 — High
**Status:** Open

Disposal saat ini hanya dilakukan dengan mengganti:

```text
status = disposed
```

Field `disposed_date` tersedia di backend, tetapi tidak tersedia sebagai input yang jelas di halaman detail.

Belum ada:

* Disposal reason
* Approval
* Disposal method
* Sale proceeds
* Buyer
* Write-off value
* Gain/loss
* Supporting document
* Approved by

Selain itu, apabila `disposed_date` kosong, fungsi depresiasi masih menggunakan tanggal hari ini.

### Tindakan

Buat workflow disposal terpisah:

```text
Active
→ Disposal Requested
→ Approved/Rejected
→ Disposed
```

### Acceptance criteria

* Status disposed wajib memiliki tanggal disposal.
* Depresiasi berhenti pada tanggal disposal.
* Proceeds dan gain/loss dihitung.
* Aset disposed tidak dapat dikembalikan menjadi active tanpa reversal resmi.
* Disposal memiliki approval dan audit trail.

## AST-007 — Link download dokumen berpotensi selalu 401

**Severity:** P1 — High
**Status:** Open

Route download menggunakan `downloadAuthMiddleware`, yang memerlukan:

* Authorization header; atau
* Query token

Namun frontend membuat URL:

```ts
`${api.defaults.baseURL}/assets/documents/${docId}/download`
```

URL tersebut tidak menyertakan token. Anchor browser juga tidak menggunakan interceptor Axios.

### Tindakan

Pendekatan yang direkomendasikan:

```ts
const response = await api.get(url, {
  responseType: 'blob'
});
```

Kemudian buat temporary object URL di browser.

Alternatif kedua adalah signed URL berumur pendek. Jangan menempatkan JWT utama berumur tujuh hari di URL.

### Acceptance criteria

* Download berhasil untuk user berwenang.
* User tanpa token menerima `401`.
* User tanpa permission menerima `403`.
* JWT utama tidak tampil pada URL dan browser history.
* Test mencakup download dokumen aset.

## AST-009 — Generator asset code masih rentan race condition

**Severity:** P1 — High
**Status:** Open

Kode aset menggunakan:

```sql
MAX(...) + 1
```

Walaupun lebih baik daripada `COUNT(*) + 1`, dua request bersamaan masih dapat memperoleh nomor yang sama.

### Tindakan

Gunakan salah satu:

* Sequence table dengan row lock
* Database-generated sequence
* Transaction dan `SELECT ... FOR UPDATE`
* Retry ketika unique constraint gagal

### Acceptance criteria

* Minimal 20 concurrent create request tidak menghasilkan nomor duplikat.
* Nomor tetap berurutan sesuai kebijakan.
* Duplicate key ditangani dengan retry, bukan HTTP `500` mentah.

## AST-010 — Model depresiasi belum membedakan aset depreciable dan non-depreciable

**Severity:** P1 — High
**Status:** Open

Master kategori mencakup `LAND/Tanah`, tetapi setiap aset dengan harga dan tanggal pembelian diproses oleh fungsi depresiasi yang sama. Master kategori hanya memiliki `requires_production_line` dan belum memiliki aturan depresiasi.

### Tindakan

Tambahkan pada kategori atau aset:

```text
is_depreciable
default_useful_life_years
default_depreciation_method
default_depreciation_rate
```

Tambahkan juga:

```text
acquisition_date
in_service_date
depreciation_start_date
```

Depresiasi seharusnya mengikuti tanggal siap digunakan sesuai kebijakan perusahaan, bukan selalu tanggal pembelian.

### Acceptance criteria

* Tanah dapat ditandai non-depreciable.
* Aset non-depreciable memiliki depresiasi nol.
* Tanggal pembelian dan tanggal mulai depresiasi dipisahkan.
* Default kategori dapat dioverride hanya oleh role berwenang.

* Tidak ada kondisi aset terlepas tetapi P&ID gagal dihapus.
* Master nonaktif tetap dapat ditampilkan dalam histori lama.

# 8. Keputusan Review

**Status: CHANGES REQUIRED**

Modul Asset Management sudah memiliki fondasi yang cukup baik untuk Asset Register dasar, tetapi belum siap dijadikan modul final karena terdapat risiko:

* Kehilangan relasi dan spesifikasi
* Kesalahan depresiasi
* Perubahan nilai historis
* Penghapusan audit trail
* Dokumen tidak aman
* Tidak adanya RBAC
* Tidak adanya test khusus asset

Manual book final belum dikunci pada tahap ini. Setelah seluruh blocker selesai dan telah diverifikasi ulang, dokumentasi modul akan ditutup dengan:

1. Flowchart final
2. Role and permission matrix
3. Business rule table
4. Database relationship/ERD
5. API reference
6. Architecture code table
7. User manual langkah demi langkah
8. Troubleshooting
9. Acceptance test result
