**Status: VERIFIED ✅**

Reversal sekarang berjalan dalam transaction dan melakukan:

```sql

WHERE id = ?
FOR UPDATE
```

# PROC-R23 — FULLY APPROVED PO MASIH BISA DIUBAH TANPA RE-APPROVAL

**Severity: P0 — Critical**
**Status: NEW / OPEN**

Ini blocker paling penting dari review kali ini.

Current PO lifecycle lock hanya aktif apabila:

```text
PO sudah mempunyai GRN
```

atau:

```text
PO sudah mempunyai pembayaran
```

Tetapi PO yang:

```text
approval_status = 2
GRN belum ada
payment belum ada
```

masih dapat diedit secara material.

Contoh:

```text
PO disetujui:

Vendor A
Qty      = 10
Price    = 100.000
Total    = 1.000.000

approval_status = 2
```

Setelah approval user dengan permission edit masih berpotensi mengubah:

```text
Vendor B
Qty      = 1.000
Price    = 500.000
Total    = 500.000.000
```

sementara:

```text
approval_status tetap = 2
```

Dengan kata lain approval lama secara efektif ikut "menyetujui" data baru yang tidak pernah diperiksa approver.

## Required Rule

### Option A — Lock

Setelah:

```text
approval_status = 2
```

field material dikunci:

```text
vendor_id
pr_id
project_id
items
quantity
unit_price
currency
discount
PPN
advance_payment
payment_term
```

Perubahan membutuhkan:

```text
Reject / Reopen PO
→ Edit
→ Approval ulang
```

### Option B — Amendment Workflow

Lebih ideal:

```text
Approved PO
   ↓
Amendment Request
   ↓
Revision No.
   ↓
Re-Approval
   ↓
Approved Revision
```

## Acceptance Test

```text
PO approval_status = 2
GRN = none
payment = none

PUT quantity berbeda
→ 409

PUT vendor berbeda
→ 409

PUT unit price berbeda
→ 409
```

Administrative field seperti:

```text
contact_person
delivery address
internal notes non-financial
```

boleh diputuskan tetap editable.

# PROC-R24 — GRN DAPAT DIBUAT DARI PO YANG BELUM DIAPPROVE

**Severity: P0 — Critical**
**Status: NEW / OPEN**

Create GRN sekarang mengunci PO dengan:

```sql
SELECT id
FROM purchase_orders
WHERE id = ?
FOR UPDATE
```

Tetapi hanya memeriksa keberadaan PO.

Belum memeriksa:

```text
is_deleted = 0
approval_status = 2
```

Artinya secara backend masih memungkinkan:

```text
Draft PO
approval_status = 0
        ↓
Create GRN
        ↓
Approve GRN
        ↓
Stock masuk
```

Ini membuat PO approval dapat dilewati.

Bahkan test Procurement saat ini banyak membuat PO dengan:

```json
{
  "status": "approved"
}
```

tetapi `POST /purchase-orders` sendiri tetap menginisialisasi:

```text
approval_status = 0
```

Jadi `status="approved"` tidak sama dengan multi-level approval.

## Required Fix

Create GRN transaction:

```sql
SELECT id, approval_status, is_deleted, status
FROM purchase_orders
WHERE id = ?
FOR UPDATE
```

Lalu:

```text
PO tidak ada            → 404
PO is_deleted = 1       → 409
approval_status != 2    → 409 PO_NOT_APPROVED
```

GRN approval juga sebaiknya melakukan defensive validation yang sama sebelum posting stok.

## Acceptance Tests

```text
Draft PO → create GRN → 409
Approval 1/2 → create GRN → 409
Approval 2/2 → create GRN → 201
Deleted PO → create GRN → 409
```

dan:

```text
PO kehilangan approval sebelum GRN approve
→ stock posting ditolak
```

# PROC-R25 — CANCELLED PR MASIH BISA DIMODIFIKASI MELALUI SEBAGIAN BID ENDPOINT

**Severity: P1 — High**
**Status: PROC-R17 PARTIAL**

Helper:

```text
getActivePurchaseRequest()
```

sudah diterapkan di banyak endpoint dan ini merupakan improvement yang benar.

Tetapi belum di seluruh subresource Bid.

Contoh endpoint yang masih bekerja langsung terhadap `pr_bids`:

```text
GET    /purchase-requests/:prId/bids
PUT    /purchase-requests/:prId/bids/:bidId
POST   /purchase-requests/:prId/bids/:bidId/select
POST   /purchase-requests/:prId/bids/:bidId/select-item/:itemIndex
DELETE /purchase-requests/:prId/bids/:bidId
POST   /purchase-requests/:prId/bids/:bidId/upload
```

Sebagian endpoint tersebut tidak memastikan:

```text
PR masih active
```

bahkan beberapa tidak memastikan:

```text
bidId benar-benar milik prId pada URL
```

## Contoh Integrity Bug

Route:

```text
/PR-A/bids/BID-B/select
```

dengan `BID-B` sebenarnya milik PR-B.

Backend memang melakukan:

```text
UPDATE ... WHERE id=BID-B AND pr_id=PR-A
```

untuk selection.

Tetapi sesudah itu vendor dibaca menggunakan:

```sql
SELECT vendor_id
FROM pr_bids
WHERE id = BID-B
```

tanpa `pr_id`.

Akibatnya `selected_vendor_id` PR-A dapat diisi vendor dari bid milik PR-B.

## Required

Buat helper:

```text
getActivePrBid(prId, bidId)
```

yang memastikan:

```text
PR active
bid exists
bid.pr_id = PR id
```

Gunakan pada seluruh Bid endpoints.

## Acceptance Tests

```text
Cancelled PR → update bid → 404/409
Cancelled PR → select bid → 404/409
Cancelled PR → upload bid document → 404/409

PR-A + Bid milik PR-B
→ select → 404
→ tidak ada data PR-A maupun PR-B yang berubah
```

# PROC-R26 — BID SUMBER PO MASIH BISA DIHAPUS PERMANEN

**Severity: P1 — High**
**Status: NEW / OPEN**

Generate PO sekarang menyimpan:

```text
purchase_orders.source_bid_id
```

Ini bagus karena memberikan source trace dan idempotency.

Tetapi endpoint:

```text
DELETE /purchase-requests/:prId/bids/:bidId
```

masih melakukan:

```text
DELETE pr_bid_items
DELETE pr_bids
```

secara permanen.

Tidak ada pengecekan apakah bid tersebut sudah menjadi sumber PO.

Skenario:

```text
PR
 ↓
Vendor quotation / bid
 ↓
Bid selected
 ↓
PO generated
 ↓
source_bid_id = 123
 ↓
DELETE Bid 123
```

Hasil:

```text
PO.source_bid_id = 123
```

tetapi dokumen keputusan procurement-nya sudah tidak ada.

Selain itu delete bid saat ini merupakan dua query terpisah dan belum transaction.

## Required

Jika bid sudah digunakan PO:

```text
409 BID_HAS_PO
```

atau logical delete/archive.

Jangan hard delete procurement decision yang sudah mempunyai downstream financial document.

Minimal:

```text
SELECT PO
WHERE source_bid_id = bidId
AND is_deleted = 0
```

Jika ada:

```text
reject deletion
```

## Acceptance Test

```text
Generate PO dari Bid
DELETE Bid
→ 409 BID_HAS_PO

Bid + Bid Items tetap ada
PO source tetap dapat ditelusuri
```

# PROC-R27 — IDEMPOTENCY GENERATED PO BERTENTANGAN DENGAN SOFT DELETE

**Severity: P1 — High**
**Status: PROC-R19 PARTIAL**

Idempotency sekarang menggunakan:

```text
UNIQUE (pr_id, source_bid_id)
```

Ini efektif mencegah duplicate generate.

Tetapi soft-deleted PO masih tetap mempunyai:

```text
pr_id
source_bid_id
```

yang sama.

Skenario:

```text
PR + Bid
  ↓
Generate PO-001
  ↓
PO-001 dibatalkan / soft delete
  ↓
Generate ulang
```

Business logic sebelumnya ingin PO cancelled tidak dianggap active downstream document.

Tetapi database tetap mempunyai:

```text
(PR, Bid) UNIQUE
```

dari PO-001.

Generate berikutnya terkena duplicate key lalu code mencari PO lama dan memasukkannya sebagai:

```text
skipped
```

Jadi sistem secara efektif tidak benar-benar dapat menerbitkan PO pengganti dari bid yang sama setelah PO lama dibatalkan.

## Required Business Decision

Pilih salah satu:

### A. Cancelled generated PO tidak boleh regenerate

Maka UI/API harus mengatakan:

```text
Restore PO lama
```

bukan generate ulang.

### B. Boleh generate replacement PO

Maka idempotency key perlu mempertimbangkan active lifecycle, misalnya revision/replacement relation.

Contoh:

```text
source_bid_id
revision_no
replaces_po_id
```

Jangan hanya menghapus unique constraint karena race protection tetap diperlukan.

