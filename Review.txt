# PROC-R14 — CONCURRENT GRN REVERSAL DAPAT MEMBALIK STOK DUA KALI

**Severity: P0 — Critical**
**Status: NEW / OPEN**

Current reversal melakukan:

1. `SELECT GRN`
2. cek `is_reversed`
3. ambil `stock_movements`
4. baru membuka transaction
5. kurangi stok
6. insert reversal movement
7. set `is_reversed = 1`

Masalahnya, langkah 1–3 dilakukan **di luar transaction**.

Dua request reversal yang masuk hampir bersamaan dapat melakukan:

```text
Request A → is_reversed = 0
Request B → is_reversed = 0

A → stock -10
A → is_reversed = 1

B → stock -10 lagi
B → is_reversed = 1
```

Reversal sequential memang sudah dites, tetapi concurrent reversal belum.

## Required Fix

Masukkan seluruh pemeriksaan ke transaction:

```text
BEGIN

SELECT goods_receipts
FOR UPDATE

cek is_reversed

SELECT stock_movements

UPDATE inventory_stocks

INSERT reversal movements

UPDATE goods_receipts

COMMIT
```

Tambahkan idempotency protection.

## Acceptance Test

Jalankan dua reversal bersamaan:

```text
Promise.all([
    reverse(grnId),
    reverse(grnId)
])
```

Expected:

```text
1 request → 200
1 request → 409

stock hanya berkurang satu kali
hanya satu reversal tercatat
```

# PROC-R15 — DUA GRN BISA DIBUAT BERSAMAAN UNTUK PO YANG SAMA

**Severity: P0 — Critical**
**Status: NEW / OPEN**

Saat create GRN backend melakukan:

```text

```

sebelum masuk transaction pembuatan dokumen.

Dua request bersamaan terhadap PO yang sama dapat melakukan:

```text
Request A → tidak menemukan GRN
Request B → tidak menemukan GRN

A → INSERT GRN
B → INSERT GRN
```

Document counter tidak menyelesaikan masalah ini karena counter hanya menjamin:

```text
GRN number unique
```

bukan:

```text
satu active GRN per PO
```

Test concurrency sekarang membuat 20 GRN untuk **20 PO berbeda**, bukan 20 request pada satu PO.

## Required Fix

Di transaction create GRN:

```sql
SELECT id
FROM purchase_orders
WHERE id = ?
FOR UPDATE;
```

Setelah memperoleh lock:

```text
validasi PO
cek active GRN lagi
INSERT GRN
```

## Acceptance Test


# PROC-R16 — DOKUMEN APPROVED MASIH DAPAT DIEDIT

**Severity: P1 — High**
**Status: NEW / OPEN**

Ini gap lifecycle yang cukup serius.

## GRN

`PUT /goods-receipts/:id` masih dapat mengubah:

```text
warehouse_id
status
received_date
notes/items
```

meskipun GRN sudah approved dan stok telah diposting.

Contoh:

```text
GRN approved:
Warehouse A
Qty = 10

Stock Movement:
Warehouse A +10

setelah itu GRN diedit menjadi:
Warehouse B
Qty = 100
```

Dokumen GRN dan stock movement tidak lagi merepresentasikan transaksi yang sama.

## PO

Approved PO juga masih dapat diedit:

```text
vendor
item
quantity
price
discount
PPN
payment terms
```

bahkan ketika downstream transaction sudah mulai berjalan.

## PR

PR yang sudah approved/PO generated masih dapat diubah melalui normal update.

## Required Lifecycle

### PR

```text
Draft → editable
Submitted → limited
Approved → financial/source data locked
PO Generated → locked
```

### PO

```text
Draft → editable
Approved → controlled amendment only
GRN exists → item/vendor/qty locked
Payment exists → financial field locked
```

### GRN

```text
Draft/Received → editable
Approved → LOCKED
Reversed → LOCKED
```

Correction GRN approved:

```text
Reversal
→ New GRN
```

bukan edit transaksi lama.


### ✅ DITERAPKAN — tim development

- **GRN**: `approval_status = 2` atau `is_reversed = 1` → 409
  (`GRN_LOCKED_APPROVED` / `GRN_REVERSED`), diarahkan ke reversal + GRN baru.
- **PO**: ada GRN aktif → `vendor_id` dan `items` terkunci
  (`PO_LOCKED_BY_GRN`); AP sudah dibayar → `advance_payment`,
  `discount_percent`, `ppn_percent`, `payment_term`, `payment_term_2`, `items`
  terkunci (`PO_LOCKED_BY_PAYMENT`).
- **PR**: sudah menerbitkan PO → `PR_LOCKED_BY_PO`; sudah disetujui penuh →
  `PR_LOCKED_APPROVED`. Field terkuncinya `notes` (item PR ada di dalamnya),
  `project_id`, `request_date`, `needed_by`.

Satu keputusan desain yang perlu kami jelaskan: **yang dikunci adalah PERUBAHAN
nilai, bukan kehadiran field di payload.**

Implementasi pertama kami menolak begitu `items` ada di request. Waktu diperiksa
ke frontend, `PurchaseOrders.vue` ternyata SELALU mengirim seluruh isi form
termasuk `items` pada setiap simpan. Artinya versi itu akan membuat PO yang
barangnya sudah datang mustahil disimpan sama sekali — termasuk sekadar mengubah
alamat pengiriman. Untuk modul yang sudah live itu bukan penguncian, itu
kerusakan.

Sekarang nilai yang dikirim dibandingkan dengan yang tersimpan (item
dinormalisasi ke bentuk kanonik lalu diurutkan). Mengirim ulang item yang sama
lolos; mengubah qty, harga, atau vendor ditolak. Perubahan administratif tetap
jalan. Keduanya ada tesnya.

# PROC-R17 — SOFT-DELETED PR BELUM BENAR-BENAR TERKUNCI

**Severity: P1 — High**
**Status: OPEN / AST-R08 PARTIAL**

List/detail/update utama sudah memfilter:

```text
is_deleted = 0
```

Tetapi beberapa endpoint berbasis `:prId` masih mengambil PR tanpa filter `is_deleted`.

Contoh:

```text
PR approval
bid creation
bid selection
bid winner
bid summary
generate PO
bid progress
```

Bahkan `POST /purchase-orders` dengan `pr_id` juga membaca PR tanpa memastikan:

```text
PR.is_deleted = 0
```

Akibatnya secara API PR yang sudah dibatalkan masih berpotensi digunakan sebagai sumber PO.

## Masalah kedua

`generate-pos` dan normal PO creation mencari existing PO:

```sql
WHERE pr_id = ?
```

tanpa filter `is_deleted = 0`.

Jadi:

```text
PR
↓
PO dibuat
↓
PO dibatalkan / soft delete
↓
Generate PO ulang
```

dapat tetap dianggap:

```text
"PR sudah memiliki PO"
```

meskipun PO tersebut sudah dibatalkan dan disembunyikan.

## Required Fix

Buat helper terpusat:

```text
getActivePurchaseRequest()
```

dan gunakan di seluruh endpoint operational.

Bedakan:

```text
active PO
historical/cancelled PO
```

Historical PO tetap tersimpan untuk audit tetapi jangan salah dianggap active downstream document.


### ✅ DITERAPKAN — tim development

Benar di kedua sisi, dan kami sudah verifikasi langsung di source.

Helper `getActivePurchaseRequest(id, columns, tx?)` dibuat sesuai saran, dipakai
di seluruh endpoint operasional: approve PR, buat bid, pilih pemenang, ringkasan
bid, generate PO, bid progress, unggah lampiran, dan pembacaan PR di dalam
`POST /purchase-orders`. Endpoint restore sengaja TIDAK memakainya — tugasnya
memang membaca PR yang terhapus.

Masalah kedua juga diperbaiki: `SELECT ... FROM purchase_orders WHERE pr_id = ?`
di `generate-pos`, di PO create, dan di pengecekan hapus PR kini menyertakan
`AND is_deleted = 0`. PO yang sudah dibatalkan tidak lagi dihitung sebagai PO
aktif milik PR, sehingga PR-nya bisa di-generate ulang.

Tes bagian 21: PR yang dibatalkan tidak bisa di-approve, tidak bisa generate PO,
tidak bisa ditambah bid — ketiganya 404.

# PROC-R18 — UPDATE PO DAPAT MEMBUAT AP / PAYMENT SCHEDULE TIDAK SINKRON

**Severity: P1 — High**
**Status: NEW / OPEN**

Pada update PO, payment schedule hanya disinkronkan ketika:

```ts
Array.isArray(items) || payment_schedules
```

Padahal schedule juga dipengaruhi oleh:

```text
payment_term
po_date
expected_date
advance_payment
discount_percent
ppn_percent
notes / contract total
vendor
```

Contoh:

```text
PO total = 100 juta
Advance = 20%
AP Down Payment = 20 juta
```

kemudian user mengubah hanya:

```json
{
  "advance_payment": 40
}
```

PO menjadi 40% advance, tetapi AP/schedule berpotensi masih 20 juta.

Lebih jauh, header/item update disimpan dalam transaction, sedangkan `upsertPaymentSchedules()` pada update masih dipanggil setelah transaction tersebut selesai.

Jadi masih mungkin:

```text
PO berhasil berubah
AP gagal berubah
```

## Required Fix

Definisikan:

```text
affectsPaymentSchedule =
items
payment_term
po_date
expected_date
advance_payment
discount_percent
ppn_percent
notes
vendor_id
```

Kemudian:

```text
BEGIN

UPDATE PO
UPDATE ITEMS
RECALCULATE TOTAL
UPDATE PAYMENT SCHEDULE
UPDATE ACCOUNTS PAYABLE

COMMIT
```

Jika `items` tidak ada pada payload, ambil current items dari database.


### ✅ DITERAPKAN — tim development

`affectsPaymentSchedule` didefinisikan persis seperti daftar reviewer: `items`,
`payment_term`, `po_date`, `expected_date`, `advance_payment`,
`discount_percent`, `ppn_percent`, `notes`, `vendor_id`, plus
`payment_schedules`.

Sinkronisasinya juga dipindah KE DALAM transaction update — sebelumnya dipanggil
setelah transaction selesai, jadi "PO berubah tapi AP gagal berubah" memang
mungkin terjadi.

Saran "kalau `items` tidak ada pada payload, ambil current items dari database"
diikuti. Ini penting: memakai array kosong akan membuat total kontrak jadi nol
dan menghapus seluruh jadwal.

Tes bagian 22 mengirim `{ advance_payment: 40 }` saja pada PO ber-DP 20% lalu
memastikan jadwal pembayarannya benar-benar berubah.

# PROC-R19 — GENERATE-PO MULTI VENDOR BELUM IDEMPOTENT

**Severity: P1 — High**
**Status: NEW / OPEN**

Pada `generate-pos`, setiap PO vendor dibuat dalam transaction masing-masing.

Contoh terdapat 3 vendor:

```text
Vendor A → PO berhasil
Vendor B → PO berhasil
Vendor C → ERROR
```

PO A dan B sudah ter-commit.

Tetapi:

```text
PR status = PO_GENERATED
```

baru di-update setelah seluruh loop berhasil.

Jika vendor C gagal:

```text
PR tetap belum PO_GENERATED
A dan B sudah punya PO
```

User retry:

```text
A → PO kedua
B → PO kedua
...
```

berpotensi menghasilkan duplicate procurement.

## Required Fix

Pilihan terbaik:

### Option A — All-or-Nothing

Seluruh generate:

```text
PO A
PO B
PO C
PR status
```

satu business transaction.

atau:

### Option B — Idempotency

Simpan relasi eksplisit:

```text
source_pr_id
source_bid_id
```

dan enforce uniqueness:

```text
(PR, Bid/Vendor)
```

Retry hanya melanjutkan yang belum berhasil.


### ✅ DITERAPKAN — tim development (Option B)

Kami pilih Option B (idempotency), bukan all-or-nothing. Alasannya: kalau vendor
C gagal karena datanya memang bermasalah, Option A akan membuang PO vendor A dan
B yang sudah benar dan memaksa seluruhnya diulang. Option B menyimpan yang sudah
berhasil dan hanya melanjutkan sisanya — itu yang lebih sesuai dengan cara orang
memakai tombol generate.

`purchase_orders.source_bid_id` ditambah, dengan UNIQUE `(pr_id, source_bid_id)`.
Percobaan kedua untuk bid yang sama ditolak database, ditangkap sebagai
`ER_DUP_ENTRY`, dan vendor itu masuk daftar `skipped` di respons — bukan error.

UNIQUE-nya sengaja mengizinkan banyak baris ber-`source_bid_id` NULL: seluruh PO
lama dan PO yang dibuat manual tidak punya nilai ini, dan MySQL tidak menganggap
NULL sebagai duplikat. Jadi tidak ada data berjalan yang terganggu.

# PROC-R20 — REVERSAL DAPAT MEMBUAT NEGATIVE STOCK

**Severity: P1 — High**
**Status: NEW / OPEN**

Current reversal:

```sql
UPDATE inventory_stocks
SET quantity = quantity - ?
```

tanpa pemeriksaan stock saat ini.

Skenario:

```text
GRN masuk +10

kemudian:
Production issue -8

Current stock = 2

User reverse GRN 10
```

hasil:

```text
Stock = -8
```

Jika negative inventory tidak diizinkan oleh business rule, reversal harus ditolak.

## Recommended

```sql
UPDATE inventory_stocks
SET quantity = quantity - ?
WHERE product_id = ?
  AND warehouse_id = ?
  AND quantity >= ?;
```

Jika affected row = 0:

```text
409 INSUFFICIENT_STOCK_FOR_REVERSAL
```

Lalu user harus melakukan stock correction sesuai approval flow.


### ✅ DITERAPKAN — tim development

Persis seperti SQL yang reviewer sarankan: `UPDATE ... WHERE ... AND quantity >= ?`,
dan `affectedRows === 0` → 409 `INSUFFICIENT_STOCK_FOR_REVERSAL`.

Responsnya menyertakan `needed` dan `available` supaya user tahu berapa yang
kurang tanpa harus menebak. Karena seluruh reversal ada dalam satu transaction
(lihat R14), penolakan ini me-rollback juga pengurangan stok item lain yang
sudah sempat diproses — tidak ada reversal separuh jalan.

# PROC-R21 — DOCUMENT NUMBER MASIH MENGGUNAKAN UTC DATE

**Severity: P2 — Medium**
**Status: NEW**

Counter sudah concurrency-safe. Itu sudah bagus.

Tetapi tanggal nomor masih dibuat dengan:

```ts
new Date().toISOString().slice(0, 10)
```

yang berarti UTC.

Untuk server/users WIB:

```text
11 Aug 2026 01:00 WIB
=
10 Aug 2026 18:00 UTC
```

nomor dapat menjadi:

```text
PR-20260810-xxxx
```

padahal tanggal bisnis sudah:

```text
11 Aug 2026
```

## Required

Gunakan satu business timezone yang eksplisit, misalnya:

```text
Asia/Jakarta
```

atau gunakan database business date yang sudah dikonfigurasi timezone-nya.


### ✅ DITERAPKAN — tim development

`businessDatePart()` memakai `Intl.DateTimeFormat` dengan `timeZone`, default
`Asia/Jakarta`, bisa ditimpa lewat env `BUSINESS_TIMEZONE`.

Dampaknya nyata: setiap dokumen yang dibuat antara 00:00 dan 07:00 WIB selama ini
bernomor tanggal kemarin.

# PROC-R22 — UPLOAD SECURITY SUDAH BAGUS, TAPI TRANSACTION CLEANUP BELUM SEMPURNA

**Severity: P2 — Medium**

Magic-byte/MIME/extension protection sudah verified. 👍

Tetapi pada multi-file bid:

```text
File 1 → write disk
DB row 1 → insert

File 2 → write disk
DB row 2 → gagal
```

catch menghapus physical files, tetapi DB row pertama yang sudah ter-insert belum otomatis rollback.

Akibatnya dapat ada:

```text
pr_bid_documents row
→ file fisik sudah dihapus
```

## Required

DB insert multi-file harus transaction.

Selain itu Procurement multer memiliki size limit tetapi belum terlihat error handler khusus seperti modul Asset; upload terlalu besar sebaiknya menghasilkan:

```text
413 Payload Too Large
```

bukan generic 500.


### ✅ DITERAPKAN — tim development

Seluruh INSERT `pr_bid_documents` untuk satu permintaan kini dalam satu
`withTransaction`, termasuk update `pr_bids.quotation_file` yang sebelumnya
dijalankan terpisah setelahnya. Kalau ada yang gagal, baris database di-rollback
dan berkas fisik yang sudah ditulis dihapus di `catch`.

`handleUploadErrors` ditambahkan pada kedua endpoint upload mengikuti pola modul
Asset: `LIMIT_FILE_SIZE` → **413**, MulterError lain → 400, bukan 500 generik.

# PROC-R12 — received_by MASIH DAPAT DISPOOF

**Severity: P2 — Medium**
**Status: STILL OPEN**

Current create GRN:

```text
received_by dari body
atau
current user
```

User A masih dapat mengirim ID User B apabila ID tersebut valid.

Recommended:

```text
created_by = current authenticated user
received_by = explicit receiver
```

dan jika receiver boleh berbeda, berikan business rule/permission khusus.


### ✅ DITERAPKAN — tim development

Diperbaiki persis seperti rekomendasi: `created_by` dan `received_by` dipisah.

Ternyata `goods_receipts` **tidak punya kolom `created_by` sama sekali** — itu
sebabnya penginput dokumen tidak pernah tercatat. Kolomnya ditambahkan lewat
`ensureGrnCreatedBy()`.

Sekarang `created_by` SELALU diambil dari token dan tidak bisa dikirim klien.
`received_by` tetap boleh diisi orang lain, karena penerima barang di gudang
memang sering bukan penginput dokumen — yang penting jejak penginputnya ada.
Kalau nanti bisnis ingin membatasi itu pun, sekarang datanya sudah tersedia untuk
diaudit.

# PROC-R13 — PARTIAL DELIVERY

**Severity: Business Gap**
**Status: DECISION REQUIRED**

Saat ini sistem tetap menerapkan satu active GRN per PO.

Namun proses procurement nyata dapat berupa:

```text
PO qty = 100

GRN 1 = 30
GRN 2 = 40
GRN 3 = 30
```

Jika perusahaan membutuhkan partial delivery, model perlu diubah menjadi:

```text
ordered_qty
received_qty
outstanding_qty
```

per PO item.

Ini bukan blocker teknis jika business memang menetapkan satu PO = satu GRN.
