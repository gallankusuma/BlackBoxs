🔴 EST-MTO-R38 — Deal masih punya two-transaction race

Ini temuan baru terpenting.

Current Deal masih mempunyai dua transaction.

Transaction 1
BEGIN


SELECT proposal FOR UPDATE
cek status


IF newStatus != deal:
    UPDATE status


IF newStatus == deal:
    TIDAK update status


COMMIT

Lalu baru:

Transaction 2
BEGIN


create Project
set project_id
copy contract MTO
UPDATE proposal → DEAL


COMMIT

Current source secara eksplisit tidak menulis status Deal di transaction pertama, kemudian membuat dealResult transaction terpisah.

Masalahnya: transaction kedua tidak re-lock dan recheck status Proposal sebelum mulai membuat Project.

Race scenario

Awal:

Proposal = SUBMITTED

Request A:

DEAL

Transaction A1:

lock Proposal
status = submitted ✅
valid
tidak update status
COMMIT

Di sela itu Request B:

SUBMITTED → REVIEW

berhasil:

Proposal = REVIEW
COMMIT

Kemudian Request A lanjut Transaction A2:

create Project
copy baseline
UPDATE Proposal → DEAL
COMMIT

Hasil akhirnya:

Request B → sukses REVIEW
Request A → sukses DEAL


final status = DEAL

Padahal saat transaction Deal sebenarnya dijalankan Proposal sudah bukan Submitted lagi.

Fix yang saya minta

Jangan dua transaction untuk Deal.

Buat satu:

BEGIN


SELECT proposal
FOR UPDATE


assert current status = 'submitted'


validate client
generate project number


INSERT project
UPDATE proposal.project_id


COPY engineering_inputs
COPY stored mto_lines


UPDATE proposal
SET status='deal',
    deal_at=NOW(),
    approved_by=?,
    approved_at=NOW()


COMMIT

Tidak perlu transaction “status validation” terpisah untuk deal.

Dengan ini:

Submitted → Review
vs
Submitted → Deal

siapa yang mendapatkan lock dulu yang menang secara deterministic.

🔴 EST-MTO-R39 — Project number masih race-prone

Di dalam Deal sekarang masih:

SELECT COUNT(*) ...

kemudian:

count + 1
→ PRJ-2026-XXXX

Masalahnya dua Proposal berbeda tidak mengunci row yang sama.

Misalnya:

Proposal A Deal
COUNT = 25


Proposal B Deal
COUNT = 25

keduanya bisa menghasilkan:

PRJ-2026-0026

Lebih mengkhawatirkan lagi, definisi client_projects yang saya temukan hanya:

project_number VARCHAR(100) NULL

tidak mempunyai UNIQUE pada project_number.

Jadi ini bukan hanya kemungkinan salah satu request gagal.

Keduanya berpotensi berhasil dengan nomor project yang sama.

Padahal repository sebenarnya sudah punya solusi concurrency-safe untuk nomor dokumen:

document_counters
(prefix, date_part)

yang dibuat karena pola MAX/COUNT + 1 sebelumnya terbukti gagal di Procurement.

Required

Gunakan atomic document counter untuk:

PRJ-2026-0001
PRJ-2026-0002
...

dan tambahkan:

UNIQUE(project_number)

sebagai database invariant terakhir.

[DEV] R39 — DITERAPKAN. estimator.routes.ts `nextProjectNumber()` +
config/database.ts `ensureProjectNumberUnique()`

Dikonfirmasi lengkap, termasuk bagian yang paling penting: tanpa UNIQUE,
KEDUANYA berhasil dengan nomor sama — bukan salah satu gagal.

1. Penomoran pindah ke `document_counters` dengan pola LAST_INSERT_ID() yang
   sama seperti procurement, di-seed dari MAX nomor yang sudah ada supaya tidak
   mundur di database yang barisnya dulu diisi COUNT()+1 atau manual.

2. UNIQUE(project_number) dipasang lewat `ensureProjectNumberUnique`. NULL boleh
   berulang di MySQL, jadi baris lama yang nomornya kosong tidak terganggu.
   Diperiksa dulu di produksi sebelum dipasang: 2 project, 2 nomor, 0 kembar.

   Kalau nanti ADA nomor kembar, index sengaja TIDAK dipasang dan dicetak
   `console.error` dengan daftar nomornya. Menomori ulang otomatis bukan pilihan
   — nomor project sudah dipakai di kontrak dan dokumen di luar sistem.

3. Satu beda sadar dari procurement: alokasi nomor di sini dilakukan DI DALAM
   transaction deal, bukan transaction terpisah. Procurement memisahkannya
   karena 20 PO serentak mengantre di baris counter. Deal terjadi beberapa kali
   sehari, jadi imbalannya lebih berharga: deal yang rollback tidak
   meninggalkan nomor hangus. Dicatat di komentar fungsinya.

Verifikasi bahwa tesnya memang bergigi: `nextProjectNumber` sementara
dikembalikan ke COUNT()+1, tes langsung jatuh ke "2 dari 5 berhasil" — pola
2-dari-20 PROC-R05 persis. Setelah dikembalikan: 5/5 berhasil, 5 nomor unik.
