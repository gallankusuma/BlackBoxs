# PROC-R01 — DELETE APPROVED GRN DAPAT MERUSAK STOCK

**Severity: P0 — Critical**
**Status: OPEN**

Ini temuan paling serius.

Posting stok baru sudah menggunakan:

```text
inventory_stocks.quantity
```

dan `stock_movements`.

Tetapi endpoint:

```text
DELETE /goods-receipts/:id
```

masih mencoba reversal menggunakan kode lama:

```sql
UPDATE inventory
SET quantity_on_hand = ...
```

Padahal implementasi posting GRN sendiri menjelaskan bahwa tabel/kolom lama tersebut tidak sesuai dengan schema aktual.

Lebih berbahaya lagi, reversal dibungkus:

```ts
safeCleanup(...)
```

yang **menelan error**.

Setelah reversal gagal, backend tetap:

```text
DELETE stock_movements
DELETE grn_items
DELETE goods_receipts
```

Sehingga dapat terjadi:

```text
Stock tetap +10

tetapi:
GRN hilang
stock movement hilang
audit trail hilang
```

Ini berpotensi menghasilkan stok tanpa dokumen sumber.

### Required fix

Approved GRN **jangan hard delete**.

Gunakan workflow:

```text
Approved GRN
      ↓
Reversal Request
      ↓
Stock Reversal
      ↓
Reverse Movement
      ↓
GRN status = reversed/cancelled
```

Semua dalam **satu transaction**.

### Acceptance Criteria

Setelah GRN +10 direverse:

```text
inventory stock = stock sebelumnya
original GRN tetap ada
original movement tetap ada
reverse movement tercatat -10
reversal reason tercatat
reversed_by tercatat
```

# PROC-R02 — APPROVED GRN DAPAT DI-REJECT TANPA REVERSAL STOCK

**Severity: P0 — Critical**
**Status: OPEN**

Endpoint:

```text
POST /goods-receipts/:id/reject
```

hanya mengecek:

```text
userLevel >= 2
```

lalu langsung mengubah:

```text
approval_status = -1
status = rejected
```

Tidak ada pengecekan apakah GRN tersebut **sudah fully approved dan stok sudah diposting**.

Skenario:

```text
PO
 ↓
GRN qty 10
 ↓
Approved
 ↓
Stock +10
 ↓
Reject GRN
 ↓
status = rejected
```

Stock masih +10.

Lebih berbahaya lagi, create GRN menganggap `approval_status = -1` sudah tidak aktif.

Jadi PO yang sama kemudian dapat dibuatkan GRN baru.

Potensi:

```text
GRN #1 → Stock +10 → Reject
GRN #2 → Stock +10

Actual stock = +20
```

padahal barang sebenarnya mungkin hanya datang 10.

### Required fix

Fully approved GRN tidak boleh menggunakan endpoint reject biasa.

Gunakan:

```text
Pending → Reject

Approved → Reversal
```

### Acceptance Criteria

```text
approval_status 0/1 → reject allowed
approval_status 2 → reject returns 409
```

dan arahkan ke reversal workflow.

# PROC-R03 — APPROVAL GRN DAN STOCK POSTING BELUM ATOMIC

**Severity: P1 — High**
**Status: OPEN**

Saat GRN fully approved:

1. `goods_receipts.approval_status = 2`
2. COMMIT
3. baru kemudian `applyGrnToInventory()` dalam transaction lain.

Kode bahkan mengembalikan pesan:

```text
Persetujuan tersimpan, tetapi posting stok gagal
```

Artinya secara desain masih memungkinkan:

```text
GRN = Approved
Stock = belum masuk
```

### Required

Full approval dan stock posting harus satu atomic transaction:

```text
BEGIN

UPDATE GRN approval

UPDATE inventory_stocks

INSERT stock_movements

COMMIT
```

Jika salah satu gagal:

```text
ROLLBACK semuanya
```

### Acceptance Criteria

Tidak boleh ada kondisi:

```text
GRN approved
AND
stock movement absent
```

# PROC-R04 — PO CREATE BELUM TRANSACTIONAL

**Severity: P1 — High**
**Status: OPEN**

Create PO sekarang melakukan:

```text
INSERT purchase_orders
↓
INSERT item 1
↓
INSERT item 2
↓
...
↓
create payment schedules
↓
create Accounts Payable
```

tetapi keseluruhan proses **belum dibungkus satu database transaction**.

Jika item ketiga gagal:

```text
PO header sudah tersimpan
item pertama sudah tersimpan
item kedua sudah tersimpan
```

Kemudian API error.

User bisa mencoba kembali dan membuat masalah baru.

### Required

```text
BEGIN

INSERT PO
INSERT PO ITEMS
INSERT PAYMENT SCHEDULE
INSERT ACCOUNTS PAYABLE

COMMIT
```

Error:

```text
ROLLBACK
```


### ✅ DITERAPKAN — tim development

Create PO kini satu `withTransaction`: header, item, jadwal pembayaran, dan AP
berhasil bersama atau tidak sama sekali. `upsertPaymentSchedules()` diberi
parameter `tx` opsional supaya ikut transaction pemanggil — tanpa itu, jadwal dan
AP tetap tersimpan meski PO-nya di-rollback.

Endpoint `generate-pos` (satu PO per vendor pemenang) juga dibungkus, per PO.
Kegagalan pada vendor ketiga tidak lagi menyisakan PO tanpa item, dan PO vendor
sebelumnya yang sudah lengkap tetap sah.

Tes bagian 7b: item kedua memakai product_id tidak ada → FK gagal → jumlah PO
tidak bertambah sama sekali.

# PROC-R05 — PERBAIKAN NOMOR DOKUMEN BELUM LENGKAP

**Severity: P1 — High**
**Status: PARTIAL**

PR sudah benar menggunakan:

```ts
withDocumentNumber()
```

dengan retry saat UNIQUE collision.

Tetapi PO create masih menggunakan:

```ts
await nextSequentialCode(...)
```

langsung.

GRN create juga masih:

```ts
await nextSequentialCode(...)
```

Dan `generate-pos` juga menggunakan generator langsung.

Jadi klaim bahwa concurrency protection sudah diterapkan ke seluruh PR/PO/GRN belum sepenuhnya sesuai source.

Test concurrency yang ada juga baru membuktikan **15 PR paralel**, belum PO dan GRN.

### Required

Semua document creation wajib melalui helper yang sama:

```text
PR
PO
Auto-generated PO
GRN
```

### Test

```text
20 concurrent PR
20 concurrent PO
20 concurrent GRN
```

Expected:

```text
20 success
20 unique number
0 HTTP 500
```


### ✅ DITERAPKAN — tim development

Benar, dan klaim kami sebelumnya memang kelewat luas: hanya PR yang lewat helper.
PO, `generate-pos`, dan GRN memanggil generator langsung. Sekarang keempatnya
lewat `withNumberedDocument()`, dan `nextSequentialCode` tidak lagi bisa dipanggil
langsung dari route.

Yang lebih penting: pendekatan MAX(...)+retry ternyata **tidak lolos kriteria
reviewer sendiri**. Diuji dengan 20 PO serentak, hanya 2 yang berhasil — tiap
putaran retry cuma meloloskan satu permintaan sampai percobaan habis. Jadi ini
bukan sekadar "belum diterapkan ke PO/GRN", mekanismenya memang tidak memadai.

Penomoran diganti dengan tabel `document_counters` + `LAST_INSERT_ID()`, atomic
per (prefix, tanggal). Dua kesalahan yang kami buat dan perbaiki saat mengerjakan
ini, dicatat supaya tidak terulang:

1. Alokasi nomor sempat ditaruh DI DALAM transaction dokumen — baris counter jadi
   terkunci sepanjang INSERT PO + item + jadwal + AP, dan 18 dari 20 permintaan
   mati di `Lock wait timeout exceeded`.
2. Ditemukan bug lama yang tidak ada di daftar review: `syncScheduleAPStatus()`
   mengambil koneksi BARU sementara transaction pemanggil masih memegang
   koneksinya. Dengan pool 10 koneksi, 20 permintaan serentak saling menunggu
   koneksi kesebelas — request menggantung, bukan melambat. Fungsi itu kini ikut
   `tx`.

Hasil akhir 20 PO serentak: 20 berhasil, 47 ms.

### Test

```
20 concurrent PR  → 20 sukses, 20 nomor unik, 0 HTTP 500  ✅
20 concurrent PO  → 20 sukses, 20 nomor unik, 0 HTTP 500  ✅
20 concurrent GRN → 20 sukses, 20 nomor unik, 0 HTTP 500  ✅
```

# PROC-R07 — PR/PO REJECT BELUM MEMERIKSA DOWNSTREAM DOCUMENT

**Severity: P1 — High**
**Status: OPEN**

PR yang sudah fully approved masih dapat di-reset menjadi pending melalui endpoint reject tanpa memeriksa apakah sudah mempunyai PO.

Demikian juga PO approval dapat di-reset tanpa business validation yang cukup terhadap:

```text
GRN
Stock Movement
Payment
Accounts Payable
```

### Recommended lifecycle

```text
PR approved + PO exists
→ tidak boleh reject biasa

PO approved + GRN exists
→ tidak boleh reject biasa

PO with payment
→ formal cancellation/reversal
```


### ✅ DITERAPKAN — tim development

Reject di modul ini artinya "kembalikan ke antrean persetujuan", jadi memang
tidak boleh dipakai kalau dokumen turunannya sudah jalan.

- Reject PR ditolak 409 `PR_HAS_PO` kalau sudah ada PO aktif yang merujuknya.
  Tanpa ini, PR jadi pending sementara PO turunannya tetap berjalan — sumbernya
  seolah belum disetujui padahal barangnya sudah dipesan.
- Reject PO ditolak 409 `PO_HAS_GRN` kalau ada GRN aktif (yang direversal dan
  yang di-reject tidak dihitung), dan 409 `PO_HAS_PAYMENT` kalau
  `accounts_payable.paid_amount` sudah terisi.

Formal cancellation untuk PO berbayar sudah tersedia lebih dulu lewat soft
delete PO yang menolak `PO_HAS_TRAIL`.

# PROC-R08 — DELETE PR MASIH HARD DELETE

**Severity: P1 — High**
**Status: OPEN**

PO sudah diperbaiki menjadi logical delete.

Tetapi PR masih:

```text
DELETE pr_bid_items
DELETE pr_bids
DELETE purchase_request_items
DELETE purchase_requests
```

dan beberapa proses cleanup menggunakan helper yang **menelan error**.

Jadi procurement sekarang tidak konsisten:

```text
PO → audit-friendly soft delete ✅

PR → permanent hard delete ❌
```

### Required

Implement:

```text
is_deleted
deleted_at
deleted_by
deletion_reason
```

PR yang:

```text
approved
punya bid
punya vendor comparison
punya downstream transaction
```

jangan dapat dihapus permanen.


### ✅ DITERAPKAN — tim development

`is_deleted`, `deleted_at`, `deleted_by`, `deletion_reason` ditambahkan lewat
`ensurePurchaseRequestSoftDelete()` — kolom baru, default 0, tidak ada data lama
yang diubah.

Aturannya: PR yang sudah disetujui **atau** sudah punya penawaran vendor hanya
bisa dibatalkan dengan alasan (soft delete). PR draft tanpa penawaran masih boleh
dihapus permanen, tapi kini dalam satu transaction dan tanpa `safeCleanup` —
penghapusan separuh jalan tidak lagi mungkin dilaporkan sukses.

Empat query PR (daftar, detail, riwayat, update) ikut memfilter `is_deleted = 0`,
dan ada `POST /purchase-requests/:id/restore` sejajar dengan PO.

Frontend `PurchaseRequests.vue` menangkap `REASON_REQUIRED` lalu meminta alasan,
supaya user tidak mentok di pesan error.


endpoint approve/reject yang memang sengaja berbasis `user_level` (alasannya di
komentar atas endpoint approve PR). Tidak ada celah lain.

# PROC-R10 — SECURITY UPLOAD QUOTATION & PR ATTACHMENT

**Severity: P1 — High**
**Status: OPEN**

Modul Asset sebelumnya sudah diperbaiki dengan:

```text
MIME validation
magic-byte validation
extension allowlist
random filename
size limit
```

Procurement belum mengikuti standard tersebut.

Saat ini bid dan PR attachment menggunakan:

```ts
multer.diskStorage
path.extname(file.originalname)
```

hanya dengan limit 10 MB.

Tidak ada:

```text
MIME whitelist
magic-byte validation
extension whitelist
malicious file detection
```

### Required

Gunakan utility upload yang sama dengan Asset Management agar security standard konsisten.


### ✅ DITERAPKAN — tim development

Kedua uploader (bid quotation & PR attachment) pindah ke `memoryStorage`, lalu
memakai `validateUpload()` + `storeValidatedFile()` dari
`backend/src/utils/file-validation.ts` — utilitas yang sama dengan modul Asset.

Artinya berlaku: whitelist ekstensi (pdf/jpg/png/docx/xlsx), MIME harus cocok
dengan ekstensi, **isi berkas dicek magic byte**, nama berkas diganti UUID, dan
limit 10 MB tetap.

Pada unggahan bid (multi-file) seluruh berkas divalidasi dulu sebelum satu pun
ditulis, dan kalau INSERT DB gagal berkas yang terlanjur ditulis dihapus lagi.

Diverifikasi di tes bagian 16: HTML ditolak, SVG ditolak, berkas bernama `.pdf`
tapi isinya HTML ditolak, PDF asli diterima.

# PROC-R11 — PATH VALIDATION DELETE ATTACHMENT LEMAH

**Severity: P1 — High**
**Status: OPEN**

Delete PR attachment hanya memeriksa:

```ts
filePath.includes('/pr-attachments/')
```

kemudian melakukan:

```ts
fs.unlinkSync(...)
```

String check tersebut belum cukup untuk mencegah path traversal.

Contoh kelas input:

```text
/pr-attachments/../../...
```

dapat tetap lolos pemeriksaan substring.

### Required

Gunakan:

```text
path.resolve()
```

lalu pastikan resolved path benar-benar berada di dalam:

```text
uploads/pr-attachments
```

Lebih baik lagi client hanya mengirim **document ID**, bukan filesystem path.


### ✅ DITERAPKAN — tim development

Benar — `/uploads/pr-attachments/../../../../etc/passwd` lolos pemeriksaan
substring.

Helper `resolveInsideUploadDir()` me-resolve path lalu memastikan hasilnya berada
di dalam direktori unggahan, memakai `base + path.sep` supaya folder bernama
mirip (`pr-attachments-lain`) tidak ikut lolos. Dipakai di dua tempat: hapus PR
attachment dan hapus dokumen bid.

Catatan implementasi: versi pertama kami mengambil `path.basename()` dari input.
Itu membuat traversal mustahil lolos, tapi berarti path jahat diterima diam-diam
seolah sah dan endpoint tetap membalas 200. Diubah supaya path di-resolve apa
adanya dan yang keluar dari folder **ditolak 400**.

Saran reviewer agar klien mengirim document ID belum dikerjakan — kontrak
`file_path` masih dipakai frontend yang berjalan, jadi perubahan itu kami pisah
supaya tidak mencampur perbaikan keamanan dengan perubahan kontrak API.

# PROC-R12 — `received_by` GRN DAPAT DIISI USER LAIN

**Severity: P2 — Medium**
**Status: OPEN**

GRN create menggunakan:

